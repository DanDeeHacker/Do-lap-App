## Findings (most severe first)

### S3 — new this run

#### F1 `test_drift_validity.py`'s four tests only pass because of test execution order, not isolation
Severity: S3 · Confidence: CONFIRMED (reproduced) · Area: Phase A / test hygiene, regression watchlist ("Sandbox diverged" family)

Location: `backend/tests/test_drift_validity.py` (all 4 tests); `backend/app/metrics/reference.py:110` (`_main_session`, opens `SessionLocal()` directly, bypassing the `db_session`/`client` fixtures); `backend/tests/conftest.py:1-6` (schema is created by `TestClient(app)`'s startup lifespan, not by fixture setup alone).

What happens: `E._drift_z_core` → `mech_priors` → `REF._main_session()` queries `models.Activity` against the app's real `SessionLocal`. That database's tables exist only after some test in the same process has opened a `TestClient`. `test_drift_validity.py`'s tests use neither `client` nor `db_session`, so standing alone they hit an uncreated schema.

Failure scenario: a developer runs `cd backend && pytest tests/test_drift_validity.py -v` while iterating on the mechanics drift core (the single most plausible thing to do while editing exactly that code) and sees 4 failures that have nothing to do with their change, with a confusing "no such table" error instead of a clear fixture-ordering message. The same would happen under `pytest-randomly` or `pytest-xdist`, neither of which this repo currently uses.

Evidence: `pytest tests/test_drift_validity.py -v` → `4 failed` (`sqlite3.OperationalError: no such table: activities`); `pytest tests/test_session_lifetime.py tests/test_drift_validity.py -q` → `7 passed` (unrelated to this file but opens a `TestClient` first) followed by `pytest tests/test_drift_validity.py -q` alone in the same run → still part of the originally-reported `963 passed` whole-suite run, confirming order (not content) is the variable.

Suggested fix: give `test_drift_validity.py` its own lightweight fixture that creates the schema (e.g. request the `client` fixture once per module, or have `conftest.py` create tables in an autouse, session-scoped fixture rather than relying on the first `TestClient` instantiation as a side effect).

Test to add: none needed beyond making the existing four tests independent of ordering — e.g. add a `pytestmark` or autouse fixture in the file itself that calls `TestClient(app)` once (discard it) before the module's tests run.

Health-risk direction: none (no runner-facing behaviour; CI is currently green).

#### F2 Clinical-record corrections/addenda are clinic-scoped, not care-assignment-scoped, unlike the rest of the documentation surface
Severity: S3 · Confidence: PLAUSIBLE (reasoned from code; intent not verified against design docs) · Area: F2 (access control), new surface

Location: `backend/app/routers/records.py:386-390` (`_own_record`: `rec.clinic_id != p.clinic_id` is the only check) vs. `:35-45` (`doc_access`, used by `get_card`/`put_card`/`documentation`/`print_doc`/`handover`/`export_doc`, which requires `has_care_assignment` for live access) and `:238-242` (`_own_episode`: requires `ep.physio_id == p.id`, stricter than `_own_record`).

What happens: `POST /api/clinical-records/{record_id}/corrections` and `.../addenda` let any physio at the same clinic amend any clinical record belonging to that clinic, even one written by a different clinician for a runner the requesting physio has never claimed and has no live or past care assignment with.

Failure scenario: Physio B, a colleague of Physio A at the same clinic but who has never treated runner R, can call `POST /api/clinical-records/{id}/corrections` for a record A wrote about R and have it accepted (404 only if `clinic_id` differs). If this is meant to be clinic-wide (continuity of care, administrative correction after a clinician leaves), it's a product decision, not a bug — but it's inconsistent with `_own_episode`'s stricter per-physio scoping right next to it, and with `doc_access`'s care-assignment check used everywhere else in the same file, which suggests it may be an oversight rather than a decision.

Evidence: static code read; not reproduced live (would need two physio demo accounts at the same clinic plus an existing clinical record — out of time budget this cycle; `havlickova@fyzioholesovice.cz` is the only seeded physio demo account, so this needs a second clinic-mate account created first).

Suggested fix: either confirm clinic-wide correction access is intended (and make `_own_episode` match it, or document why episodes and records differ), or add a `has_care_assignment`-or-past-assignment check to `_own_record`.

Test to add: two physios at the same clinic, one with no assignment to the runner, asserting 403 (if the decision is per-assignment) or documenting the clinic-wide intent in a passing test (if it's a decision).

Health-risk direction: false alarm/privacy — not a scoring defect, a clinical-record access-scope question.

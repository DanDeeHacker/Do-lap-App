AI agent review guidelines

Rules and a step-by-step procedure for AI agents that repeatedly screen the Došlap app for defects and propose improvements. Specific to this app, written to stay valid when files move or are renamed. Version 2 (5 Oct 2026) — highlighted text is new since version 1 (25 Sep 2026).

AudienceAn AI coding agent (e.g. Claude Code) with shell access to the repository, run on a schedule or on request. Humans can use it as a checklist too.
OutputA review report (section 9) with evidence-backed findings, improvement proposals and coverage gaps. Read-only by default.
Two depthsQuick screen (section 10, ~15–30 min) for frequent runs; full review (section 5, phases A–J) weekly, after large changes, or when the quick screen finds something.
Companion docsThe newest Documentation/Engine_Doslap_v*_dokumentace.pdf (engine design, formulas, evidence; source Documentation/engine/) and the most recent report in Documentation/reviews/ on branch claude/reviews.

0. The one principle: contracts, not paths

Everything in this playbook is written as behavioural contracts (invariants the app must keep) plus discovery searches that find the code responsible for each contract. File paths are given only as hints valid on 5 Oct 2026. When a hint no longer matches:

  1. find the code by its role with the discovery search in section 4 (search by function or concept, not by path);
  2. run the check against the new location;
  3. record the move under “Structural drift” in the report and propose the playbook update;
  4. if you cannot find a responsible component at all, report it as a coverage gap — never skip a check silently.

1. Rules of engagement (hard rules)

  1. Read-only by default. Do not edit code, data, configuration, tests or documentation unless the task explicitly asks for it. Describe fixes in the report (a diff sketch is fine).
  2. Never touch production or real people’s data. No mutating calls to the deployed app, no real Garmin or Apple accounts, no real runner data. Run everything against a throwaway database that the app seeds itself (appendix A).
  3. No data to external AI services during review. Leave NVIDIA_API_KEY, LLM_API_KEY, ASSISTANT_API_KEY, EMBED_API_KEY, VISION_API_KEY and ASR keys unset; the LLM features then fall back to rule-based output. Never paste runner data into web tools.
  4. Never commit, push, rebase, reset or discard on the code branches. Uncommitted changes and untracked files belong to the owner: note them in the baseline, never clean them up. Reports are the one exception: they are committed only to branch claude/reviews (never merge main into it, never force-push).
  5. Evidence before assertion. Every finding needs a location (file:line), a concrete failure scenario and evidence: a failing test, script output, a screenshot, or a precise code-path argument. Label it CONFIRMED (reproduced) or LIKELY / PLAUSIBLE (reasoned, not reproduced).
  6. Never weaken tests or thresholds to get green. A failing test is a finding.
  7. Respect product decisions (section 2). You may question them, but as a “Product question”, never as a bug.
  8. Verify every citation (authors, title, journal, year, volume, pages, DOI and what the study actually found) against PubMed, the publisher or an institutional repository before proposing it; flag existing references that overstate their evidence.
  9. Both directions of health risk are defects. False reassurance (missing a real overload, suppressing a needed physio referral) and false alarms (alarm fatigue, needless referrals) both count; say which one a finding causes.
  10. Czech is the product language. Judge UI copy by Czech conventions (formal “vy”); the English UI is a translation layer (section 3) — check it for untranslated Czech, never propose dropping Czech.
  11. Engine time is pinned. Reason about windows with the engine’s own “today” (the thread-local today override used by history replays), never with the wall clock.
  12. Keep the repository clean. Scratch scripts, screenshots and databases go to a temporary directory — including one-off test files: never drop a scratch test into backend/tests/.
  13. Be honest about coverage. List every check that could not run and why.

3. Orientation — what the app is

  • Architecture: one container. FastAPI backend (SQLAlchemy; SQLite locally, Postgres when DATABASE_URL is set) serves a React + Vite single-page app from the same origin; CSRF protection is a same-origin check. Czech UI with a British English translation layer: Czech strings are the keys (scripts/i18n/en/*.json → frontend/src/i18n/en.json via scripts/i18n/merge.py).
  • Roles: runner, physio, employer, partner, plus the owner (admin view, engine tools). The UI offers runner sign-in only.
  • Data in: Garmin (export import, live sync with stored tokens and a pre-07:00 auto-sync, per-second detail streams, all-day heart rate, ride/swim HR traces), Apple Health (import and push webhook, sleep stages, night HRV), self-report (check-ins, run ratings with pain points, OSTRC injury reports, shoes, races, profile incl. menstrual cycle).
  • Engine out: an assessment with three axes (mechanika / zátěž / příznaky), overall score, tier, quadrant (threshold 25 with hysteresis 18), a ranked signal list, triage decision, capacity picture and (v3) daily guidance plus readiness, critical speed (Rychlost), illness and cycle-aware signals. History views replay the engine day by day on a pure in-memory snapshot of the runner’s data (RunnerData.as_of).
  • Reports: morning/evening report cards, the Monday weekly plan, optional AI notes.
  • Tools around it: Excel backtests (v1 vs v2), a sensitivity sandbox that mirrors the scoring, signal documentation, a physio AI brief, a per-tab AI assistant with evidence cards, self-management exercise programmes.

5. Full review — step by step

Run the phases in order. Each item is a check with its pass condition. Record PASS / FAIL / NOT RUN for every item in the report. Phases are independent enough to run in parallel (e.g. sub-agents for E+G, F, H, I) on separate throwaway databases and ports; the lead re-verifies every S1/S2 before reporting it.

Phase A — Baseline

  1. A1 What changed: git status, git log since the last report in Documentation/reviews/ (on claude/reviews), diff stat. Focus on changed areas first. If the last report’s commit is unreachable (history rewritten), say so and use git log --since=<report date>.
  2. A2 Environment: Python virtualenv (Python ≥ 3.12; .python-version pins 3.13) and Node dependencies present; note versions.
  3. A3 Backend tests: run the full suite. Pass: all green. Record count, skips and duration ({{TBD-TESTS}}). A duration jump > 2× without new tests is a finding (or machine load — rerun once).
  4. A4 Frontend: type-check and production build must succeed with no errors.
  5. A5 Python import sanity: python -m compileall all backend modules (catches syntax errors in scripts tests don’t import).

Phase B — Map and structural drift

  1. B1 Run every discovery search from section 4; record the current location of each role.
  2. B2 List routers and count endpoints; list models and columns; list frontend routes and tabs. Compare with the previous report — new endpoints, tables, columns, tabs and engine modes need the targeted checks in phases C–H.
  3. B3 Note any role that disappeared or split; propose the playbook update.

Phase C — Engine correctness (highest priority)

  1. C1 Mode plumbing. Every engine mode appears consistently in: the switch endpoint’s allowed list (unknown modes are rejected), the version suffix map and its reverse lookup, the frontend mode union types, the Data-page options, the v3-only Trénink nav gate, the history cache key. Search for direct comparisons of the engine mode (e.g. _emode() ==) across all of backend/app; each must be intentional — “sensitive mechanics” must use the shared helper that includes v2 and v3 (_sensitive()).
  2. C2 Time. Inside the engine and metrics code, no wall-clock calls (datetime.now, date.today, time.time) except the engine’s own today helpers and the documented weekly-frozen population priors (reference._real_today). Windows use the engine’s day helpers; date strings are compared on the date part ([:10]).
  3. C3 Replay parity. Start from the one read, load_runner_data (section 4): every table it loads is an engine input and must reach both the replay (via as_of) and the history-cache digest, so a change to it invalidates the cached history. Pass: for v1, v2 and v3 — including a runner with stored streams and a v3 runner with a shoe — the history’s last point equals the live assessment on all axes and the quadrant. Also switch a runner’s engine with mechanics in the 18–25 hysteresis band and compare live vs history.
  4. C4 Caches. History cache keyed by engine version + history version and invalidated on every recompute. Every module-level cache in the metrics code (lru_cache, _…CACHE) must key on everything that changes its result — a data fingerprint (segment count, stream fetch time, profile hash), never ids alone. Probe: compute, mutate the data behind the same ids, recompute in the same process.
  5. C5 Direction and units. Every scored mechanics metric has a risk direction; scores and v2/v3 flags are one-sided (an improvement never raises a warning); coupled metrics (vertical ratio + oscillation; cadence + stride) count once for convergence. Per-run and segment drift are both in session typical-error units.
  6. C6 No rounded values in scoring. Values rounded for display must never feed back into points (use exact fields).
  7. C7 Capacity invariants (v3). Per-run ceiling = capacity × (1 + margin) × readiness; readiness factor within 0.70–1.00; injury history applied once (margins), not also as a multiplier; runs followed by pain ≥ 3/10 within 72 h excluded from capacity; ≥ 3 prior runs in 30 days before a per-run capacity exists; ≥ 4 weeks before a weekly one. Margin narrowing factors (novice year, new-shoe transition, under-conditioning) never push the margin below SHRINK_MIN.
  8. C8 Guidance invariants (v3). Every type’s km ≤ min(per-run ceiling, weekly budget left); running exactly the ceiling adds no load points; overrides exactly as in section 2; quality only per section 2 (readiness ≥ 65 %); taper and deload applied; “předběžné” until today’s sleep/HRV; paces inside the runner’s own observed speed range; ≤ 45 min in Z4+ per quality session. The evening report’s “Zítra” and “Zbytek týdne” and the weekly plan obey the same overrides.
  9. C9 Sandbox parity. For every engine mode, seeding the sandbox from a live assessment reproduces the live load and mechanics axes exactly. Every new signal must exist in both places.
  10. C10 Statistics. p-values from Student’s t with the right degrees of freedom; FDR on unrounded p; context model (speed, gradient, time, surface) used where available; out-of-domain segments not scored; minimum sample sizes respected.
  11. C11 Stream pipeline. Durations from timestamps, never row counts; QC acceptance enforced; units normalised; any change to segmentation bumps the segmentation version so stored streams are re-fetched.
  12. C12 Numerical robustness. Division by zero, None / empty inputs, zero or negative durations, profiles with < 2 points, HR max ≤ resting HR, NaN. Probe with degenerate synthetic runners (one run; no HR; no daily data; identical values).
  13. C13 Performance. Live assessment ≤ 0.3 s for a 6-month runner with streams; a 183-day history replay ≤ 20 s in every mode (v3 is the slowest). Look for quadratic work inside per-segment or per-session loops and for recomputation a cache should cover.
  14. C14 Docs match code. Formulas and constants in docstrings, signal documentation, info texts and the engine documentation PDF equal the constants in code (check ~15 constants each review, incl. readiness bands, ACWR bands, pain thresholds, windows).

Phase E — Data ingestion and integrations

  1. E1 Imports and syncs are idempotent: re-importing / re-syncing never duplicates activities or daily metrics. A file re-import never deletes runner-entered data (manual activities, run ratings and pain points, exclusions, hand-edited days) or another provider’s history. Run import tests with SQLite foreign keys enforced (or on Postgres).
  2. E2 Garmin rate limits (HTTP 429) stop the batch without marking runs as failed; genuine failures are marked so the backfill advances; stale streams are re-fetched; refresh failures keep the old data (running and HR-only streams); a failed HRV / resting-HR range call is filled in by a later sync.
  3. E3 Stored tokens are encrypted when the secret is configured; a revoked token disables auto-sync with a visible error; a transient Garmin error (network, 5xx) never disables auto-sync; every auto-sync failure is written to the runner’s last error.
  4. E4 The daily auto-sync runs in Europe/Prague time before 07:00 (time-zone-aware, independent of the container TZ, across DST), and failures for one runner never stop the others.
  5. E5 Apple push webhook requires its token; unknown payloads are rejected with 400, not partially stored and never 500; the token never appears in logs; sleep and steps are de-duplicated across sources like the file import.
  6. E6 Cross-training reaches the load axis but never the running mechanics.

Phase F — API, security and privacy

  1. F1 Every mutating route (POST / PATCH / PUT / DELETE) carries the CSRF dependency, or is a documented exemption. Known exemptions (5 Oct 2026): the sandbox’s simulate and sweep (stateless), the Apple push webhook (token), operator-token routes guarded by require_feedback_token (annotations export/resolve, assistant ops/*). Known accepted item: logout has no CSRF check (S3 — a cross-site request can only log the user out). Probe a foreign Origin, Origin “null”, a look-alike host, a foreign Referer without Origin, and no Origin/Referer at all. {{TBD-CSRF}}
  2. F2 Every runner-scoped route calls a runner access check (read access, self) or a role requirement, and every nested object id is checked to belong to that runner. Probe IDOR with two runner accounts and a physio who has not claimed the runner: each must get 403/404 for foreign data. Probe the physio claim: claiming a closed case, a runner without consent, another physio’s case or after the runner revoked you → refused; public registration with a non-runner role → refused.
  3. F3 Session cookie: HttpOnly, Secure over HTTPS, SameSite; argon2 password hashing; login throttle active and not bypassable by rotating X-Forwarded-For; session tokens stored hashed; “log out all devices” revokes every session.
  4. F4 The JSON export and logs contain no passwords, tokens or session secrets; secret files stay git-ignored and docker-ignored.
  5. F5 External LLM calls happen only as in section 2 (AI features), send the minimum data, have timeouts and a fallback, and are labelled as AI output. For each call site, check the consent gate with a mocked LLM that must not be called without consent.
  6. F6 Uploads: size limits and zip handling (no path traversal, no zip bombs — check the uncompressed size before extracting), malformed files return a clear 400.
  7. F7 GDPR: physio and owner access to a runner is written to the access log and visible to the runner — including routes outside /api/runners/{rid}/ (AI brief/chat, RTR, conclusions, physio bootstrap, sandbox inputs).

Phase G — Persistence, migrations, deployment

  1. G1 Every new or changed model column has an additive startup migration that works on SQLite and Postgres, with a backfill where old rows need a value.
  2. G2 Seeding is idempotent and never overwrites existing accounts; demo accounts exist on already-seeded databases.
  3. G3 The container builds (frontend then backend); the health endpoint reports database persistence honestly; DEPLOY.md lists every environment variable the code reads (search os.environ / getenv).

Phase H — Frontend and UX

Drive the real app in a headless browser (appendix A) for at least: one v1 demo runner and one v3 demo runner, at 1360 px and 400 px width, browser locale cs-CZ, time zone Europe/Prague. Before full-page screenshots, inject CSS that disables animations — the app uses scroll-driven reveal animations, so off-screen content otherwise renders transparent. That artefact is not a bug.

  1. H1 Every tab loads with no console errors and no horizontal overflow (scrollWidth − clientWidth = 0) on both widths.
  2. H2 The Trénink tab appears only for v3 runners, next to Dnes; switching engines on the Data page (owner only) updates navigation.
  3. H3 Consistency: the quadrant on Dnes, the Zátěž and Pohyb headlines, the last point of each history chart and the morning/evening/weekly reports agree with the live assessment and guidance.
  4. H4 Numbers: decimal comma, sensible rounding, paces as m:ss (never “5:60”), Czech dates, units always shown.
  5. H5 Czech copy: diacritics, prepositions (v / ve), formal “vy”, no English leftovers, consistent terms (Zátěž, Pohyb, Příznaky, Kapacita, Připravenost, norma); every new metric has an info text. One pass with English selected: no untranslated Czech.
  6. H6 Empty, loading and error states render (new runner with no data; network error). A failed load never shows a reassuring state (no default “Stabilní”, score or tier).
  7. H7 Tap targets ≥ 20 px on phones; text contrast readable on the dark theme.

Known environment noise in the cloud sandbox: fonts.googleapis.com fails with a certificate error; a native date input follows the browser’s UI locale (mm/dd/yyyy in an en-US Chromium) — neither is an app defect.

Phase I — Content, evidence and regulatory

  1. I1 No diagnosis or treatment claims; every guidance and risk view carries the not-a-medical-device note; pain always routes to a physiotherapist, never to a diagnosis. Self-management programmes: matched to the marked area exactly (no substring matches across regions), no diagnosis links or cure wording, with a referral note for red flags. Check the English translations too.
  2. I2 Evidence grades (A/B/C) match the cited evidence; every reference is verifiable and correctly described (design, population, sample size, significance — a feasibility study or a non-significant result must not be described as establishing a fact; a working assumption is labelled as the app’s, not attributed to a study).
  3. I3 The engine documentation in Documentation/ reflects current behaviour and version; stale sections are findings.

Phase J — Improvement proposals

  • Propose an improvement only with: the observed problem and its evidence, the expected benefit (safety, validity, clarity, speed), cost and risk, and how to validate it (test, simulation or backtest).
  • Prefer changes that improve safety and measurement validity over cosmetic ones; avoid churn.
  • Separate quick wins (< 1 hour, low risk) from larger work; flag anything that changes scores for existing runners (needs an engine version bump and a calibration run).

S4 ImprovementNo defect — a proposal (phase J).
ConfidenceMeaning
CONFIRMEDReproduced (failing test, script output, screenshot).
LIKELYStrong code-path evidence, not reproduced.
PLAUSIBLENeeds verification; say what would confirm or refute it.

8. Deciding what is a finding

  • Report behaviour that breaks a contract in this playbook, a test, the engine documentation or a product decision — or that a runner or physio would reasonably consider wrong.
  • Don’t report style preferences, hypothetical attacks without a path, or “could be refactored” without a benefit.
  • Merge duplicates: one root cause = one finding, listing all symptoms.
  • Before reporting, try to disprove the finding (look for a guard elsewhere, a test that covers it, a documented decision). Keep only what survives.

Appendix B — Calibration recipes

Synthetic runner → real drift core. Create ~90 days of runs (≈ 4/week) as simple objects with started_at, distance_km, duration_min, surface, ascent/descent and the metric (e.g. vert_ratio_pct = 8.0 + 0.3·N(0,1)). Pin the engine’s today and mode, call the per-run drift function over many runners and count how often z ≥ 0.6 and how often the flag helper returns the flag. Variants: heavy-tailed noise; a shift of +1 SD in the last 14 or 5 days (detection); an improvement of −1 SD (the flag must stay 0); easy pace +25 s/km with metrics following speed (pace confound — measure the flag over all mechanics metrics, with a matched no-slowdown baseline; helper tests/test_drift_validity.py::_history(slow=25)).
